## ‏`Rc<T>`، Smart Pointer مبتنی بر Reference Counting

در بیشتر موارد، Ownership کاملاً روشن است: دقیقاً می‌دانید کدام متغیر مالک یک مقدار مشخص است. بااین‌حال، موقعیت‌هایی وجود دارد که ممکن است یک مقدار Ownerهای متعددی داشته باشد. برای مثال، در ساختارهای دادهٔ Graph، چند Edge ممکن است به یک Node اشاره کنند و از نظر مفهومی، تمام Edgeهایی که به آن Node اشاره می‌کنند مالک آن هستند. تا زمانی که Edgeای به یک Node اشاره می‌کند و در نتیجه Ownerای برای آن وجود دارد، نباید آن Node را پاک‌سازی کرد.

برای فعال‌کردن Multiple Ownership باید به‌صورت صریح از Type به نام `Rc<T>` در Rust استفاده کنید. `Rc` مخفف **Reference Counting** است. Type به نام `Rc<T>` تعداد Referenceهای یک مقدار را دنبال می‌کند تا مشخص کند آیا هنوز از آن مقدار استفاده می‌شود یا خیر. اگر هیچ Referenceای به یک مقدار وجود نداشته باشد، می‌توان آن را پاک‌سازی کرد؛ بدون اینکه هیچ Referenceای نامعتبر شود.

`Rc<T>` را مانند تلویزیونی در اتاق نشیمن یک خانواده تصور کنید. وقتی یک نفر برای تماشای تلویزیون وارد اتاق می‌شود، آن را روشن می‌کند. افراد دیگر نیز می‌توانند وارد اتاق شوند و تلویزیون تماشا کنند. وقتی آخرین نفر اتاق را ترک می‌کند، تلویزیون را خاموش می‌کند؛ زیرا دیگر کسی از آن استفاده نمی‌کند. اگر کسی درحالی‌که دیگران هنوز مشغول تماشای تلویزیون هستند آن را خاموش کند، تماشاگران باقی‌مانده اعتراض خواهند کرد!

زمانی از Type به نام `Rc<T>` استفاده می‌کنیم که بخواهیم داده‌ای را روی Heap تخصیص دهیم تا بخش‌های مختلف برنامه بتوانند آن را بخوانند و در Compile Time نتوانیم تعیین کنیم کدام بخش آخرین نفری خواهد بود که استفاده از داده را به پایان می‌رساند. اگر می‌دانستیم کدام بخش آخر از داده استفاده می‌کند، می‌توانستیم همان بخش را Owner داده قرار دهیم و قوانین معمول Ownership که در Compile Time بررسی می‌شوند، اعمال می‌شدند.

توجه کنید که `Rc<T>` فقط برای سناریوهای Single-threaded مناسب است. در فصل ۱۶ و هنگام بررسی Concurrency، روش انجام Reference Counting در برنامه‌های Multithreaded را یاد خواهیم گرفت.

باید یک دستور `use` اضافه کنیم تا `Rc<T>` وارد Scope شود؛ زیرا این Type در Prelude قرار ندارد. در تابع `main`، لیستی شامل مقدارهای `5` و `10` ایجاد می‌کنیم و آن را داخل یک `Rc<List>` جدید در متغیر `a` قرار می‌دهیم. سپس هنگام ایجاد `b` و `c`، تابع `Rc::clone` را فراخوانی می‌کنیم و Referenceای به `Rc<List>` موجود در `a` را به‌عنوان آرگومان به آن می‌دهیم.

می‌توانستیم به‌جای `Rc::clone(&a)`، عبارت `a.clone()` را فراخوانی کنیم؛ اما Convention در Rust این است که در این موقعیت از `Rc::clone` استفاده کنیم. پیاده‌سازی `Rc::clone` برخلاف پیاده‌سازی متد `clone` در بیشتر Typeها، از تمام داده یک Deep Copy تهیه نمی‌کند. فراخوانی `Rc::clone` فقط Reference Count را افزایش می‌دهد و این کار زمان زیادی نمی‌برد. در مقابل، Deep Copy کردن داده می‌تواند بسیار زمان‌بر باشد. با استفاده از `Rc::clone` برای Reference Counting، می‌توانیم از نظر بصری میان Cloneهایی که Deep Copy انجام می‌دهند و Cloneهایی که فقط Reference Count را افزایش می‌دهند تمایز قائل شویم. هنگام جست‌وجوی مشکلات عملکردی در کد، کافی است Cloneهای Deep Copy را بررسی کنیم و می‌توانیم فراخوانی‌های `Rc::clone` را از این نظر نادیده بگیریم.

### افزایش Reference Count با Clone کردن

مثال Listing 15-18 را تغییر می‌دهیم تا هنگام ایجاد و از بین رفتن Referenceها به `Rc<List>` موجود در `a`، تغییرات Reference Count را مشاهده کنیم.

در Listing 15-19 تابع `main` را تغییر می‌دهیم تا لیست `c` در یک Scope داخلی قرار بگیرد. به این ترتیب می‌توانیم ببینیم وقتی `c` از Scope خارج می‌شود، Reference Count چگونه تغییر می‌کند.

می‌بینیم که `Rc<List>` موجود در `a` در ابتدا Reference Count برابر با ۱ دارد؛ سپس هر بار که `clone` را فراخوانی می‌کنیم، این مقدار یک واحد افزایش می‌یابد. وقتی `c` از Scope خارج می‌شود، Reference Count یک واحد کاهش پیدا می‌کند. برای کاهش Reference Count لازم نیست تابعی را فراخوانی کنیم؛ برخلاف افزایش آن که با `Rc::clone` انجام می‌شود. پیاده‌سازی Trait به نام `Drop` هنگام خروج یک مقدار `Rc<T>` از Scope، Reference Count را به‌صورت خودکار کاهش می‌دهد.

چیزی که در این مثال نمی‌بینیم، این است که وقتی `b` و سپس `a` در پایان تابع `main` از Scope خارج می‌شوند، Reference Count به صفر می‌رسد و `Rc<List>` به‌طور کامل پاک‌سازی می‌شود. استفاده از `Rc<T>` اجازه می‌دهد یک مقدار چند Owner داشته باشد و Reference Count تضمین می‌کند تا زمانی که دست‌کم یکی از Ownerها وجود دارد، مقدار معتبر باقی بماند.

`Rc<T>` از طریق Immutable Referenceها به شما اجازه می‌دهد داده را برای خواندن میان بخش‌های مختلف برنامه به اشتراک بگذارید. اگر `Rc<T>` امکان داشتن چند Mutable Reference را نیز فراهم می‌کرد، ممکن بود یکی از قوانین Borrowing در فصل ۴ نقض شود: چند Mutable Borrow به یک محل یکسان می‌توانند باعث Data Race و ناسازگاری داده شوند. اما امکان تغییر داده بسیار کاربردی است! در بخش بعد، الگوی Interior Mutability و Type به نام `RefCell<T>` را بررسی می‌کنیم که می‌توانید آن را همراه با `Rc<T>` به کار ببرید تا با این محدودیت Immutable بودن کار کنید.
